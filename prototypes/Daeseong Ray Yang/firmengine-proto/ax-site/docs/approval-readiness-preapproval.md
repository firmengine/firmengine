# FirmEngine AX — 인가 전 증거·계산·법률 검토 재구성 (P0-09A)

기준: 2026-10-30, 작업 이슈 #11. 이 문서는 **코드 추가의 범위**를 기록합니다. 운영 DB/Cloudflare 배포·실 사건 적용·법률적 정확도 검증을 뜻하지 않습니다.

## 서비스 핵심 범위
- **신청 준비 → 접수 → 보정 및 개시 검토 → 채권/변제계획/채권자집회 검토 → 인가결정 전**.
- 메인 질문: 지금 확보된 서류에서 무엇을 읽었고, 실제 어느 피처를 증명하며, 소득/채무/재산/생계비/변제 관련 산식은 어떻게 계산됐고, 인가 준비를 위해 어떤 사실·서류·법률 검토를 보완해야 하는가?
- 법원에서 실제로 발부한 **보정명령**과 시스템이 근거상 검토를 권하는 **내부 예상 보완 쟁점**을 구분한다.
- **인가 이후 변제이행·면책·종결은 이번 작업 범위에서 제외**한다. 기존 절차 기록과 저장데이터는 변경·삭제하지 않는다.

## 처음 추가된 기능 (P0-09A)
- `lib/approval-readiness.ts`: 기존 사건 사실의 ID·canonical ID·대상·기간·원문 페이지·인정상태·금액을 보존한 read-only 피처 목록. 기존 계산결과의 식·입력·출처 피처 ID·차단/잠정/계산됨을 함께 제공한다.
- 기존 `caseRequirementMonitor`의 **현재 상담 요청 / 사건 업무에 반영된 요구 / OCR 문서 종류 후보 / 갈음 판단**을 별개로 읽는다. 상담 요청이 사건 업무로 연결되지 않았을 때 자동 충족 금지.
- 현재 원본/계산 데이터 버전에 결속된 `listCaseLawgraphReview`의 95 위험항목을 보존한다. 오래된 결과·항목 일부 미검토·기준정보 불일치가 발생하면 재검토를 요청하고 이전 체크를 최신 통과로 표시하지 않는다.
- 피처 미입력·계산 미확정·서류요구 미충족·법률 미판단을 **근거와 후속 조치가 있는 내부 보완 작업 초안**으로 표시한다. 현재 상태에서는 AI가 가정 수치를 생성하거나 법원 인가 여부를 확정하지 않는다.
- `GET /api/cases/{id}/approval-readiness`: 기존 getCase 인증·동일 출처 경계를 사용한 **조회 전용** 엔드포인트. `?expectedRevision=N` 으로 판본 고정 조회 가능.
- `tests/approval-readiness.test.ts`: 원문 피처/수식, 누락 vs 0, OCR 후보 vs 서류 충족, 현행 vs stale 법률판단, 법원 실제 보정 vs 내부 권고, 인가 이후 범위 제외를 검증하는 합성 테스트 6개.

## 보존·안전성
1. 기존 상담 85종, OCR 693 canonical 필드, 기존 18 계산·91 입력, 위험 95/예외 46, 관련 저장 테이블, 기준정보 버전, 사람 검토/제출 게이트 **변경하지 않음**.
2. 신규 `lib`/조회 라우트/테스트만 추가. DDL과 기존 데이터 이동 없음. 이 조회는 서류 미제출을 자동 인정하거나 기존 OCR을 다시 쓰지 않음.
3. null·미관측·상충·오인식·0·명시적 비해당은 서로 다르게 유지. PDF 원문을 근거 없이 AI가 채우지 않음.
4. 버전이 달라지거나 DB 스테이지 확인이 실패하면 최신 계산/법적 판단 완료로 보고하지 않음.
5. 법률 자문과 법원 인가결정은 **담당 변호사·법원의 권한**. 예측 확률 제공 금지.

## 추가로 반영한 판단 단위 연결 (P0-09B 초기)
- `lib/approval-issue-graph.ts`: 기존 95개 위험 ID를 **누락 없이** 각각 판단단위로 표시. 기존 LawGraph 검토 상태, 근거 법령 ID, 승인된 피처 OR-그룹, 기존 계산 출력·후속 계산 의존관계, 부족 피처의 역질문을 한 객체에 결합한다.
- `legalEvidenceInventory`의 관할·시행일 조건에 따라 **담당자 승인된 피처/산식 계약만** 법률상 증거 경로로 사용한다. 미승인·미정의 95 위험항목은 `unmapped_or_not_applicable`로 남기며 필요한 법적 피처를 AI 추정으로 확정하지 않는다.
- 현재 `Fact`의 canonical ID로만 직접 연결하고, 현재 원문 계보 점검과 `verified+accepted`를 만족하는 Fact ID만 유효 경로로 기록한다. 단순 이름/문자열 유사도는 법률 근거가 아니다.
- `getCalculationSpecs()`의 `dependsOn`을 이용해 특정 계산 결과 누락이 **어느 다른 계산 모듈에 전파되는지** 추적한다. 이 관계가 실제 법률 판정 변경 또는 유효한 금액 시뮬레이션을 의미하지 않는다.
- 읽기 API의 `judgmentGraph` 필드에 원본 정보/계산/법률 상태를 결합해 제공한다.
- `tests/approval-issue-graph.test.ts`의 합성 테스트 4개를 추가했다. **현재 피처 그룹의 법적 적합성 실측, 실제 변호사 승인, 법원 판단 정확도는 여전히 미검증**.

## 검증/배포 상태
- 신규 순수 분석 모듈을 별도 Node 22 TypeScript-strip 환경에서 격리 합성 회귀 **38/38**(인가 준비도·법률 계약·5단계 감사·조건부 시뮬레이션·실제 보정명령별 자료 검토·물리 OCR 저장현황) 실행함. 이 결과는 운영 통합이나 법률 판단 정확도를 인증하지 않음.
- GitHub main에서의 완전한 npm ci / 전체 테스트 / Next 빌드 / D1·R2 / 실제 사이트 배포 및 실제 사건 적합성은 **아직 미검증**.
- 기존 코드 수정 및 운영 마이그레이션은 없음. 다른 작업자의 main 변경이 본 기능에 미친 영향은 추후 CI와 함께 재검사 필요.

- 인가 이전의 **폐지(discontinued)**는 인가 후 단계로 잘못 분류하지 않는다. 승인(approved)/면책(discharged)만 이 초기 조회의 인가 후 범위로 분리한다. 폐지 전후 후속 절차·불복 판단은 별도 승인형 절차 계약이 필요하다.

## 저장된 계산과 현재 재실행 결과의 일치성 보강
- 현재 계산 헤드의 사건 판본/원본 버전/입력해시/기준정보 해시를 확인하고, 핵심 계산 출력(기존 자동 초안 요구 금액 및 청산가치 비교)을 현재 계산기로 다시 읽은 결과와 원 단위로 대조한다.
- `case_calculation_features`의 출력이 없거나 중복, 비정상 JSON, 허용되지 않은 상태, 값 불일치 또는 DB 조회 오류이면 `calculation.persistedCurrent=false`로 처리하고 계산·법률 최신판본으로 표시하지 않는다. 기존 계산 원장이나 원천은 수정하지 않는다.
- 추가 합성 테스트 2개로 null/0 구분, 결손/중복/비정상 JSON 및 금액 차이를 차단하는지 확인했다.

## 최신 P0-09 확장

`GET /api/cases/{id}/approval-readiness`는 `storedOcrCoverage`와 5단계 `stageAudit`를 함께 제공한다. `storedOcrCoverage`는 활성 PDF의 committed OCR head/원본 SHA/각 canonical ID의 실제 관측·미관측 상태를 D1에서 집계한다. 자세한 91입력/42출력·42 합성사례 + 3 대법원 판례 테스트는 `docs/preapproval-calculator-91-input-matrix-20261030.md`, `docs/preapproval-5-stage-case-regressions-20261030.md`. 단위테스트 합격은 운영 D1/법원 인가 판단 성능 인증이 아니다.
