# 상담 기반 필요서류 체크리스트

## 목적과 범위

의뢰인의 상담이력을 저장하고, 상담에 명시된 여러 사건 특성을 분류한 뒤 **저장된 조건 규칙으로 준비할 증빙서류를 매칭**한다. 개인사업자·급여소득자 중 하나만 고르는 방식이 아니라 소득원·채무계약·차량·가족·과거 사건을 각각 구분한다.

초기 기준정보는 **분류 피처 49개, 증빙서류 74종, 매칭 규칙 54개, 출처 11개**다. 이 숫자는 등록 범위이며 분류 정확도나 모든 현실 사건에 대한 완전성 점수가 아니다. 기준정보 편집 후에는 현재 저장 판본의 숫자를 확인한다.

이 기능은 의뢰인이 준비할 증빙을 안내한다. 신청서·채권자목록·재산목록·수입지출목록·변제계획안의 작성은 기존 문서작성 단계에서 수행한다. 상담 결과를 사건의 인정 사실로 자동 반영하거나 제출을 승인하지 않는다.

## 이용 흐름

1. 사건 작업공간의 **상담 기반 서류 체크리스트**에서 의뢰인 설명과 상담일을 저장한다.
2. **상담 분류 · 서류 매칭**을 실행한다. 기존 서버의 `gpt-6-luna`와 연결된 키를 사용한다.
3. 모델은 등록된 피처 ID, 대상, 상태, 현재·과거 구분, 상담 원문 인용을 반환한다. 서류를 자유롭게 만들어 반환하지 않는다.
4. 서버가 인용의 실제 존재·위치, 허용된 ID·상태·대상 형식을 검증하고 조건 규칙을 실행한다.
5. 서류별 대상·기간·발급처·필드·요청 이유·근거 인용·적용 규칙·출처·대안을 확인한다. 추가 질문의 답변은 새 상담이력으로 저장한 뒤 재분류한다.
6. **의뢰인 안내문 복사**는 검토할 안내문을 클립보드에 만든다. 메시지를 자동 발송하지 않는다.

단순 후속 메모가 이전 진술을 자동 폐기하지 않는다. 명확한 정정은 해당 상담의 **정정 기록**으로 저장하여 `supersedesId`로 연결하며, 정정 전 원문은 보존한다.

## 분류·매칭의 경계

| 상황 | 처리 원칙 |
| --- | --- |
| 개인사업과 근로소득을 함께 진술 | 각각의 소득원에 서류를 매칭하고 겸업 목록을 추가한다. |
| 여러 은행·카드·차용계약 | 채권자 이름만으로 병합하지 않고 계약별 대상을 유지한다. |
| 배우자가 사업하거나 부모 차량을 이용 | 신청인의 사업·차량 소유로 바꾸지 않는다. |
| 리스·렌트 차량 | 계약·보증금·인수조건을 확인하며 차량 전체를 본인 재산으로 만들지 않는다. |
| 과거 폐업 후 현재 취업 | 과거 사업과 현재 근로를 분리하고 폐업 정산자료를 사건 이력으로 매칭한다. |
| 이전 사건의 보정명령 | 현재 사건의 제출의무로 승격하지 않고 적용 사건을 다시 확인한다. |
| 상담에 언급되지 않은 항목 | 비해당으로 추정하지 않는다. 주요 미확인 항목은 추가 질문으로 남긴다. |
| 명시적 부정과 긍정이 함께 존재 | 대상·시점을 대조하고 충돌을 보존한다. 최신 문장이라는 이유로 덮어쓰지 않는다. |
| 서류 없음·미신고·발급 곤란 | 금액 0원·채무 없음·검증완료로 바꾸지 않고 대체자료 또는 확인 질문을 제시한다. |

분류 상태는 `present / absent / unknown / conflict / legal_review`이고 근거의 성격은 항상 `client_report`다. 서류 안내 상태는 `requested / qualification_needed / conflict / legal_review`이며, 제출·충족·사실 인정 상태와 다르다. 인용이 원문과 일치한다는 검증만으로 그 해석의 의미적 정확성까지 입증되지는 않는다.

## 기준정보와 저장 스키마

논리적 기준정보 스키마는 `IntakeCatalog`의 `features`, `documents`, `rules`, `sources`로 분리한다. 현재 물리 저장은 이 객체를 버전별 JSON payload로 보관하는 구조이며, 네 개의 개별 정규화 테이블을 만들었다는 의미는 아니다.

| 테이블 | 보관 내용 |
| --- | --- |
| `intake_catalog_versions` | 기준정보 판본, 스키마 버전, 전체 payload, SHA-256, 저장자·시각 |
| `intake_catalog_head` | 현재 활성 기준정보 판본과 해시 |
| `consultation_notes` | 사건별 순번, 상담 원문, 원문 해시, 상담일, 정정 연결, 작성자·시각 |
| `consultation_heads` | 상담이력 버전과 현재 분석 실행 ID |
| `consultation_runs` | 실행 fingerprint, 사건·상담·기준정보 판본, 대기·완료·실패 상태, 결과 payload와 해시 |

기준정보 수정 API는 이전 판본을 덮어쓰지 않고 새 판본을 추가한다. 상담 수정도 새 정정 기록을 추가한다. 실행 영수증에는 사건 revision·storage token·전체 입력 해시, 상담이력 해시, 기준정보 버전·해시, 엔진·프롬프트·모델 버전, 사용량을 기록한다. 결과에는 당시 피처·규칙 이름과 출처 스냅샷을 보존하고 전체 규칙은 해당 기준정보 판본으로 추적한다.

저장 시에는 읽었던 판본·해시가 여전히 같은지 확인하는 CAS 조건을 사용한다. 분석 중 사건·상담·기준정보가 바뀌면 예전 결과를 현재 결과로 채택하지 않는다. 동일 입력 fingerprint의 완료 결과는 재사용하고, 진행 중 중복 실행은 거부한다. 조회 시 저장 해시를 검증하고 오래된 결과에는 재분류 필요 사유를 표시한다.

## 규칙을 고치는 방법

**중요 데이터 관리 → 서류 안내 기준**(`/data/checklist`)에서 규칙·서류 종류·출처·판본 이력을 확인한다.

- **규칙**: 대상 범위, 모두 충족할 조건(`all`), 하나 이상 충족할 조건(`any`), 사용 여부, 요청서류, 기간, 요구 수준, 대체자료, 추가 질문을 편집한다. 조건이 없는 공통 규칙은 사건 범위에서만 허용된다.
- **서류 종류**: 이름·분류·발급처·목적·확인할 필드·기존 workflow 문서 연결을 편집한다. 새 서류를 추가한 뒤 규칙에 연결할 수 있다.
- **관할·출처**: 특정 법원 기준은 해당 관할을 지정한다. 빈 관할 목록은 공통 규칙이다. 근거 출처와 적용 위치를 확인하고 요구 수준을 선택한다.
- **저장**: 조회한 `expectedVersion`으로 새 판본을 저장한다. 다른 편집이 먼저 저장되면 409를 반환한다. 새 기준을 적용하려면 사건의 상담 분류를 다시 실행한다.

새 피처·출처의 스키마 전체 편집은 카탈로그 API 계약을 따른다. 현재 화면의 규칙 조건 선택은 등록된 피처를 사용한다. 자유로운 실행 코드나 SQL을 규칙에 넣는 방식이 아니다.

요구 수준은 `recommended`(사전 준비 권장), `required_when_applicable`(적용 범위에 해당하면 필요), `court_ordered`(현재 법원 명령 확인 필요)를 구분한다. 대안은 `any_of` 또는 `review_required`를 명시하며, 초기 대체 증빙은 적용 요건을 담당자가 확인하도록 설정했다.

같은 서류·대상·기간이 여러 규칙에서 매칭되면 근거와 workflow 연결을 보존하며 병합한다. 해당 관할 규칙의 요구 수준이 더 강하면 이를 반영한다. 관할이 불명확한 규칙은 공통 권장자료를 확정 의무로 바꾸지 않는다.

| 상담 내용 | 매칭 방향과 확인사항 |

| “개인사업자로 카페를 운영한다.” | 영업 확인, 월별 매출·비용·순소득, 매입매출·필요비 자료. 등록 유무·명의·과세유형을 질문한다. |
| “사업자등록은 없다.” | 미등록 여부를 명시적으로 보존한다. 실제 영업·계약자료의 대체 가능성을 검토하며 존재하지 않는 등록증을 강제하지 않는다. |
| “은행 대출 두 건과 카드론이 있다.” | 계약별 현재 채권자·원금·이자·잔액 기준일. 카드 이용·대출·결제는 중복하지 않는다. |

| “보험은 있지만 대출은 없다.” | 보험 환급금 자료를 안내하며 보험 가입만으로 보험대출 자료를 요구하지 않는다. |

## 화면·API·구현 위치

| 구분 | 경로·계약 |
| --- | --- |
| 사건 상담 화면 | `/cases/{caseId}/consultation` |
| 기준정보 관리 | `/data/checklist` |
| 상담 조회 | `GET /api/cases/{caseId}/consultations` |
| 상담 추가·정정 | 같은 경로에 `POST`: `action="append"`, `text`, `expectedConsultationRevision`, 선택적으로 `occurredAt`, `supersedesId` |
| 분류·매칭 실행 | 같은 경로에 `POST`: `action="analyze"`, `expectedCaseRevision`, `expectedConsultationRevision`, `expectedCatalogVersion` |
| 기준정보 조회·수정 | `GET /api/checklist-catalog`, `PUT`은 `{catalog, expectedVersion}` |
| 핵심 모듈 | `lib/intake-types.ts`, `intake-catalog.ts`, `intake-classifier.ts`, `intake-engine.ts`, `intake-store.ts` |

API는 기존 동일 출처·서버 접근 경계를 사용한다. 상담은 건당 16,000자, 활성 원문 합계 40,000자, 이력 100건 제한이며 초과 원문을 몰래 잘라 분석하지 않는다. 보호 실사건 및 `structuredTest`·`referenceTest` 원본 평가사건에는 상담 추가·분류 실행을 허용하지 않는다. 전용 상담용 사건으로 검증하며 OCR이나 원본 fixture를 변경하지 않는다.

## 검증 상태의 기록 원칙

전체 회귀검사는 실제 subprocess 실행으로 **654/654 통과**했다. 그중 이번 기능 검사는 엔진 37개·저장 계층 15개로 **52개**이며 TypeScript 검사와 배포 build도 통과했다. 기준정보 스키마·참조 검사와 규칙 엔진 검증은 모델의 의미 분류 정확도 평가와 구분한다.

배포 후 실제 유료 모델을 호출한 합성 상담 사례의 결과는 코드 판본과 연결된 별도 검증 영수증으로 남긴다. 대표 사례의 통과나 모델 호출 성공도 전 사례 정확도 검증을 뜻하지 않는다. 로컬 미리보기의 브라우저 접근이 거부되고 운영 화면은 로그인 단계에서 제한되어 화면 렌더 검수에는 제약이 있다. 배포·검증 영수증에서 실제 완료 범위를 확인한다.

실제 호출에서 동일 부재 대상의 이름 표기 차이와 잘못된 전역 부정 ID로 분류 검증이 중단되는 사례를 확인했다. engine/prompt 3판은 같은 대상의 모든 진술이 명시적 비해당인 경우에만 이름 표기를 정리하고, 정확히 `scope:none`으로 반환된 명시적 비해당에 한해 등록 피처의 범위로 ID를 복구한다. 원문 인용 검증은 계속 필수이며 긍정·미확정 대상의 서로 다른 이름이나 잘못된 ID는 임의 병합·복구하지 않는다. 프롬프트는 구체적인 ID 예시를 사용하고 출력 스키마도 허용된 접두어로 제한한다.
