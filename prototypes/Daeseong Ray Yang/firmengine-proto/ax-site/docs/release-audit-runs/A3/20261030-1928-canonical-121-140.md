## 3. 읽기 전용 사업자 동일성 감사 P1 — 실제 반례와 수정 제안

**소스 근거(원본 main blob)** `lib/business-identity-crosswalk.ts` = `73331de276f9bc78e2c9d43fc48e179cf6ba161c`.

- **P1-A 값 상충의 허위 출처 검증 완료**: `valid()`가 `Fact.value`와 현재 `Fact.rawValue` 불일치를 검사하지 않았다. 원문 사업자번호가 `987-65-43210`인데 보관된 typed 값이 `123-45-67890`인 합성 사건도 `registrationRows.verifiedSource=true`. 사업장 이름 `A` vs 원문 `B`도 `ownerEvidenceVerified=true`. 실제 법률 승인 결과는 아니지만, 사람 검토 화면에서 낡은 원천값을 확인 완료처럼 표시할 위험.
- **P1-B 누락 사업자번호가 원문 맥락 전체 은닉**: `business_registration::status`/공동사업자/개업일 원문만 있을 때 `registrationRows.length=0`; 발급서류 확인/역질문 후보가 조회되지 않는다.
- **P1-C 문서별 행 ID 충돌**: VAT와 비용 문서에 같은 로컬 `subjectId`가 발생하면 기존 `sourceRecords`와 `amountIndex`가 ID 하나만으로 병합되어 `businessSourceRows.length=1` 및 사업주/금액 대응 혼재. 별도 sourceFamily로 분리하면 2개 독립 직원 검토 후보가 된다. 실제 저장이 현재 이 충돌을 허용하는지는 staging 별도 확인해야 하지만, read-only 감사의 방어적 분리는 안전하다.
