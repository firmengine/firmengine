## 3. P1 결함 재현: 같은 페이지의 다른 사람 Fact로 증거 요건 충족 오판 가능

**실제 `main`의** `lib/feature-lineage-audit.ts::evaluateCaseFieldLineage().referenced()` callback은 `requirementId + subjectLinkId`의 승인된 **document match**와 동일 문서/페이지/hash만 검사하고, **Fact.subjectId와 confirmed SubjectLink.typedEntityId의 동일 주체 여부를 확인하지 않았다.** 하나의 PDF 페이지에 A/B 두 사람의 같은 canonical 값을 가진 Fact가 있으면 B도 A의 증빙 건수에 포함될 수 있다. `document-substitution.ts`에서는 이미 `fact.subjectId === subjectLink.typedEntityId`를 요구하므로 두 경로가 불일치한다.

**합성 입력**: A에 대한 confirmed 주체링크, A의 requirement와 해당 문서 D:1 accepted match, 동일 페이지의 Person-A/Person-B Fact, 각각 올바른 hash/quote. **독립 예상**: A fact만 A 요건에 해당; B fact는 source-only로 보존하되 A의 요건을 충족하지 않는다. **V8 실제 실행**: main 원본 callback은 B를 **true**로 반환(거짓 증거 허용); Draft PR #54 callback은 B **false**, A **true**. 다른 사람/미확정 link/무link/타페이지/변경hash/철회match 등 **10개 실제 callback 격리 조건 10/10 기대와 일치**. 이는 공개 고객자료가 아닌 **가상 데이터**이다. **전체 `evaluateCaseFieldLineage` 모듈 실행 또는 Node 테스트 통과를 의미하지 않는다.**

**[Draft PR #54](https://github.com/firmengine/firmengine/pull/54)**: 주체 링크가 confirmed이고 실제 `typedEntityId===fact.subjectId`일 때에만 기존 source ref+match 확인; 이전 합성 fixture 2건에 주체 링크를 명시하고 새 다인물 테스트를 작성했다. **프로젝트 Node22 테스트/빌드/CI·staging D1/R2·실제 다인물 OCR·공식 Word/PDF·변호사 검토 미실행**. 동일 파일의 기존 미병합 A3 PR #22/#26/#30/#51과 충돌 통합 필요. 과거 사건의 subject link 대상 ID 정합성과 구판본 마이그레이션 영향은 전문가·운영 담당자 검토 후 별도 병합하며 `main`에는 이 코드를 적용하지 않는다.
