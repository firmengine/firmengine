# 구현 범위와 검증 경계

작성 기준일: 2026-10-26. 이 문서는 새 `firmengine-proto-retry`의 현재 소스와 [`양대성-feature.md`](../../../../docs/specs/양대성-feature.md)를 기준으로 작성했다. 명세의 10절을 1~9절보다 우선하며, 기존 프로토타입의 구현·평가 기록은 이 문서의 근거로 사용하지 않는다.

목표 흐름은 **의뢰인 증빙 → 사실 후보·근거 → 인정값 → 계산·보완 판단 → 편집형 서류 → 생성본별 담당자·변호사 검수**다. 현재 결과물은 이 흐름을 실행할 수 있는 로컬 프로토타입이다. 실제 사건에 대한 제출 품질, 법원 접수·인가, 작성시간 20% 단축을 검증 완료한 제품으로 표현하지 않는다.

## 계산·n8n의 구분

`workflows/calculators.js`가 공통 계산 원본이다. `workflows/build_workflows.py`가 동일 코드를 n8n Code 노드에 삽입한다. API는 n8n 생존·준비·계산 Webhook을 각각 확인하고, Webhook이 등록된 경우 `n8n-code` 경로를 사용한다. 반환된 코드 SHA-256이 현재 소스와 다르면 계산을 채택하지 않는다.

Webhook이 준비되지 않으면 같은 파일을 로컬 Node 프로세스로 실행하며 `engine=local-node`와 경고를 남긴다. 로컬 Node 계산 성공을 n8n 워크플로 실행 성공으로 집계하지 않는다. 격리 실행 경로는 `.local/n8n`, 기본 n8n 포트는 5681이며 다른 인스턴스의 DB를 수정하지 않는다.

`workflows/law-watch.json`은 Asia/Seoul 09:00 조회 정의지만 `active:false`다. 계산 워크플로의 연결과 일일 법령 갱신의 활성·발화는 서로 다른 확인 항목이다.

## 생성본과 검수

새 생성물은 미검토 초안이다. 생성 시 사건 버전·산식 판본·계산 코드 해시·서식 매핑 판본·파일 SHA-256을 기록한다. HTML 미리보기와 편집형 파일은 같은 데이터 모델로 만들어지며 파일 다운로드 시에도 해시를 확인한다.

검수는 해당 사건 버전의 해당 파일에만 남길 수 있다. 같은 생성본의 담당자 확인이 있어야 변호사 확인을 남길 수 있다. 새 사건 버전이 생기면 이전 파일과 확인 이력을 보존하되 현재본 검수로 사용하지 않는다. 검수 과정에서 원본 파일 바이트를 바꾸지 않으며, 검수 메타데이터는 별도 기록표로 내려받는다.

현재 생성 조건이 검사하지 않는 서식 항목에는 `확인 필요`가 남을 수 있다. 이를 자동으로 식별해 최종 검수를 차단하는 포괄적 서식 검증은 구현되지 않았다. 따라서 현재 앱의 `검토 완료`는 실제 파일을 확인한 로컬 검수 기록이며, 누락 없는 법원 제출 품질 인증을 의미하지 않는다.

## 저장·삭제·기록

사건 원장·비공개 호출기록·원본·생성물은 `.local/`에 저장하며, 환경변수 `FIRMENGINE_DATA_DIR`로 원장과 객체 저장 경로를 변경할 수 있다. 원본과 생성물에는 `storage_provider`, `namespace`, `object_key`, SHA-256을 남긴다. 실제 클라우드 제공자 교체·Google Workspace 인증·동기화는 없다.

브라우저에 사건 내용을 영속 저장하지 않는다. 서버의 사건은 화면 닫기·재시작·60분 미사용으로 삭제되지 않는다. 보관은 원본·생성물·이력을 유지하고, 삭제 API는 사건 원장·작업·호출·검수 행과 연결된 원본·생성물 객체를 제거한다.

추출 성공 페이지의 캐시에는 후보 사실과 호출 감사기록이 포함될 수 있다. 사건 삭제 함수는 현재 사건과 신뢰한 캐시 연결 식별자의 해시 디렉터리를 `ROOT/.local`과 설정된 `LOCAL` 양쪽에서 찾아 경계를 확인한 뒤 제거한다. 생성물 파일뿐 아니라 같은 생성 디렉터리의 매니페스트·본문 모델도 함께 제거한다. 캐시 작성 경로 자체의 설정 통일과 실행 중 사건 삭제·지연 완료 후 재기록 방지는 별도 검증이 남는다. 명시적 정리 코드가 있다는 사실을 모든 동시 실행 상황의 완전 삭제 검증으로 해석하지 않는다.

## 실행 상태와 검증 기록의 해석

합성 스모크와 브라우저 확인은 연결된 화면·CRUD·계산·생성·검수·모바일 배치의 검증이다. 브라우저 확인에서는 JavaScript 페이지 오류와 모바일 수평 넘침이 없었다. 이는 실제 사건 본문의 정확도·전문가 검증 산식·법원 제공 양식 대응·작성시간 목표 달성의 근거를 대신하지 않는다.

페이지 API 오류는 논리 문서의 실패·확인 필요 상태와 호출 감사기록에 남는다. 현재 집계는 증빙 페이지 전체 API 실패를 `failed`, 성공·실패 혼재 또는 판독 불가·대기·매핑 검토를 `partial`로 구분한다. 추출이 끝나도 누락·판독 불가 feature가 있으면 문서를 `needs_review`로 유지한다. 작업의 기술적 완료와 필요한 모든 사실의 입증·서류 품질 성공은 별개이며, 화면의 `completed`만으로 제출 품질 성공을 선언하지 않는다.

이 문서에는 실제 샘플의 본문·정답·평가 결과를 넣지 않았다. 실제 증빙만을 사용한 새 실행과 독립평가의 결과는 별도 평가 기록을 확인해야 한다.
